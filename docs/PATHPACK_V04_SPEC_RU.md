# Техническое задание: CodeGraph-RAG / PathPack v0.4

## 1. Общая информация

**Проект:** CodeGraph-RAG  
**Алгоритм:** PathPack  
**Версия:** 0.4  
**Язык:** Python  
**Назначение:** исследовательская библиотека для поиска релевантного исходного кода в больших репозиториях с ограниченным бюджетом токенов.

Проект разрабатывается для Gemma 4 Developer Agent Paper Track.

**Главная задача:** улучшить существующий алгоритм PathPack, который использует граф зависимостей Python-кода для формирования контекста небольших локальных языковых моделей.

Работать с существующим репозиторием v0.3. Не создавать новый независимый проект. Перед изменениями изучить архитектуру, интерфейсы, тесты, систему оценки и форматы результатов.

Не переписывать работающие модули без необходимости. Сохранить возможность запуска предыдущих версий алгоритма.

## 2. Исходная проблема

Существующий PathPack v0.3 выполняет следующие действия:

1. Анализирует Python-репозиторий с помощью AST.
2. Строит граф функций, классов, импортов и вызовов.
3. Использует BM25 для поиска релевантного кода.
4. Расширяет поиск с помощью графовых зависимостей.
5. Ранжирует найденные функции.
6. Формирует ограниченный по токенам контекст для LLM.

Однако эксперименты на SWE-bench Verified выявили несколько проблем.

### 2.1. Результаты PathPack v0.3

На 20 dev-задачах получены следующие показатели:

| Метрика | 1024 | 2048 | 4096 |
|---|---:|---:|---:|
| File Recall | 0.325 | 0.575 | 0.625 |
| Function Recall | 0.075 | 0.125 | 0.175 |
| Среднее число использованных токенов | 816.8 | 1835.75 | 3827.7 |

Для сравнения, предыдущий PathPack:

| Метрика | 1024 | 2048 | 4096 |
|---|---:|---:|---:|
| File Recall | 0.400 | 0.600 | 0.575 |
| Function Recall | 0.125 | 0.125 | 0.175 |

**Важно:** версия v0.3 пока не превосходит v0.2 по всем метрикам.

### 2.2. Основные недостатки

**Проблема №1. Неэффективное использование бюджета**

Алгоритм оставляет свободные токены, поскольку работает преимущественно с целыми функциями.

При бюджете 1024 токена используется примерно 80% доступного контекста.

**Проблема №2. Низкий Function Recall**

Граф помогает находить нужные файлы, но не всегда конкретные функции, связанные с ошибкой.

**Проблема №3. Недостаточная диагностика**

Пока сложно понять, почему алгоритм выбирает одни функции и отбрасывает другие.

**Проблема №4. Необходимость проверяемой научной новизны**

Нужно экспериментально определить, какой вклад в качество поиска дают графовые зависимости, разбиение функций и алгоритм упаковки.

# 3. Основные задачи PathPack v0.4

Реализовать пять компонентов:

1. Adaptive AST Chunking
2. Hybrid Function Ranking
3. Budget-Aware Context Packing
4. Retrieval Diagnostics
5. Ablation & Benchmark Framework

Каждый компонент должен быть независимым, тестируемым и отключаемым через конфигурацию, где это применимо.

# 4. Adaptive AST Chunking

## 4.1. Цель

Научиться выбирать не только функции целиком, но и полезные фрагменты внутри длинных функций.

Необходимо уменьшить потери токенов без существенной потери контекста.

## 4.2. Требования

Использовать Python AST для разбиения исходного кода.

Поддерживать:

- обычные функции;
- асинхронные функции;
- методы классов;
- вложенные функции;
- декораторы;
- длинные тела функций;
- многострочные выражения;
- обработку исключений;
- ветвления и циклы.

Для каждой функции сохранять:

- имя;
- полное квалифицированное имя;
- путь файла;
- начальную и конечную строку;
- сигнатуру;
- родительский класс или функцию;
- список чанков;
- связи с графом зависимостей.

Каждый чанк должен иметь стабильный идентификатор.

Пример:

`src/auth.py::AuthService.login::chunk_2`

Идентификаторы должны быть детерминированными при повторном анализе неизменённого репозитория.

## 4.3. Стратегия разбиения

**Маленькие функции**

Если функция помещается в установленный размер чанка, сохранять её целиком.

**Средние функции**

Разбивать на логические блоки, ориентируясь на AST-узлы и границы инструкций.

**Большие функции**

Разбивать тело на последовательные небольшие чанки. Если один AST-узел слишком велик, разрешается дополнительное разбиение по строкам исходного кода.

Необходимо по возможности избегать разрыва небольших логических конструкций.

Однако чанки предназначены для чтения LLM и не обязаны быть самостоятельно исполняемым Python-кодом.

## 4.4. Размеры

Сделать параметры конфигурируемыми:

- `target_chunk_tokens`: 128
- `max_chunk_tokens`: 256
- `min_chunk_tokens`: 32
- `chunk_overlap_lines`: 2

Это начальные значения для экспериментов, а не доказанные оптимальные настройки.

Не создавать пустые или бессмысленные чанки ради соблюдения размера.

Большие функции должны содержать достаточно контекста для понимания каждого фрагмента. При необходимости добавлять короткую информацию о сигнатуре и родительском классе.

Стоимость этой информации обязательно учитывать в токенах.

## 4.5. Наследование графовых связей

Каждый чанк должен сохранять связь со своей исходной функцией.

Если `login()` вызывает `get_user()`, чанки `login()` наследуют информацию о связи между соответствующими функциями.

При этом не создавать искусственные вызовы между всеми чанками.

Поддерживать два уровня представления:

**Function Graph:** граф функций и их зависимостей.

**Chunk Index:** набор фрагментов, каждый из которых связан с узлом Function Graph.

Это позволит использовать существующий граф, не превращая его в чрезмерно большой граф мелких фрагментов.

## 4.6. Тесты

Проверить корректное разбиение:

- короткой функции;
- длинной функции;
- метода класса;
- вложенной функции;
- асинхронной функции;
- функции с декораторами;
- функции с многострочным выражением;
- файла с синтаксической ошибкой.

При невозможности разобрать файл записывать диагностическую ошибку, не прерывая анализ всего репозитория.

# 5. Hybrid Function Ranking

## 5.1. Цель

Разработать прозрачный механизм оценки релевантности функций и их чанков.

Использовать текстовую релевантность и графовую структуру одновременно.

Не добавлять нейросетевую модель ранжирования на этом этапе.

## 5.2. Компоненты оценки

Для каждого кандидата вычислять:

**Lexical Relevance**

Соответствие текста кода описанию ошибки на основе BM25.

**Symbol Relevance**

Совпадение идентификаторов, имён функций, классов, модулей и путей файлов с запросом.

**Graph Proximity**

Расстояние от кандидата до релевантных начальных функций в графе вызовов и зависимостей.

**Context Diversity**

Дополнительная полезность кандидата относительно уже выбранного контекста.

**Token Cost**

Количество токенов, необходимое для передачи фрагмента в модель.

## 5.3. Базовая формула

Предлагается начать со следующей функции:

`S(c) = 0.45 * L(c) + 0.20 * N(c) + 0.25 * G(c) + 0.10 * D(c)`

Где:

- `L(c)` — нормализованная лексическая релевантность;
- `N(c)` — совпадение имён и символов;
- `G(c)` — графовая близость;
- `D(c)` — полезность с учётом разнообразия контекста.

Влияние стоимости можно оценивать отдельно:

`U(c) = S(c) / (tokens(c) + 32) ** 0.5`

Это стартовая эвристика, которую необходимо проверить экспериментально.

Не считать её научно оптимальной.

## 5.4. Нормализация

Все компоненты ранжирования должны иметь понятный диапазон значений.

Не смешивать напрямую ненормализованные оценки BM25 и графовые расстояния.

Реализовать стабильную нормализацию и обработку случаев, когда все значения одинаковы.

Все коэффициенты должны настраиваться через конфигурацию.

## 5.5. Graph Proximity

Использовать существующий граф зависимостей.

Учитывать:

- прямые вызовы;
- обратные вызовы;
- импорты;
- наследование, если оно уже корректно извлекается парсером;
- расстояние до исходных функций.

Начальное максимальное число переходов: `2`.

Сделать параметр конфигурируемым.

Например:

`login() -> authenticate() -> get_user()`

Если запрос связан с `login()`, функция `get_user()` может быть полезна, даже если её название отсутствует в описании ошибки.

Не считать все типы графовых рёбер одинаково надёжными. При наличии информации о типе связи предусмотреть разные веса.

Не выдумывать связи для динамических вызовов, которые статический анализ не смог разрешить.

## 5.6. Устранение избыточности

Алгоритм должен избегать ситуаций, когда весь бюджет занимают почти одинаковые функции.

Добавить штраф за:

- дублирующиеся строки;
- сильное пересечение чанков;
- повторное включение одного и того же тела функции;
- избыточные фрагменты из одного файла.

Но не вводить жёсткое ограничение количества функций из одного файла: иногда исправление действительно требует анализа нескольких связанных функций в одном модуле.

## 5.7. Объяснимость

Для каждого выбранного чанка сохранять:

- итоговую оценку;
- BM25 score;
- Symbol score;
- Graph score;
- Diversity contribution;
- Token cost;
- причину выбора;
- путь в графе до начальной функции, если он существует.

Эта информация используется для анализа результатов и не должна автоматически передаваться LLM, расходуя её контекст.

# 6. Budget-Aware Context Packing

## 6.1. Цель

Собирать максимально полезный контекст при ограничении размера.

Поддерживать бюджеты:

- 1024 токена;
- 2048 токенов;
- 4096 токенов.

Дополнительно разрешить произвольный пользовательский бюджет.

## 6.2. Основное требование

**Контекст должен быть вложенным при увеличении бюджета.**

При одинаковом запросе, графе и конфигурации содержимое, выбранное для 1024 токенов, должно сохраняться при увеличении бюджета до 2048 и 4096.

Не допускается, чтобы увеличение бюджета приводило к исчезновению уже выбранных фрагментов.

## 6.3. Алгоритм упаковки

Реализовать детерминированный процесс:

1. Построить список допустимых чанков.
2. Оценить их релевантность.
3. Сформировать единый порядок добавления чанков, не зависящий от конкретного бюджета.
4. Учитывать зависимости между чанками: фрагмент тела функции должен сопровождаться минимальным контекстом, позволяющим понять, какой функции он принадлежит.
5. Собрать единый поток контекста.
6. Для каждого бюджета использовать максимально длинный допустимый префикс этого потока.

Если чанк не помещается, не изменять ранее сформированный контекст ради более дорогого кандидата.

При необходимости разбивать крупные чанки на меньшие атомарные фрагменты до этапа ранжирования.

Ключевой принцип: **порядок выбора не должен меняться при изменении бюджета**.

Динамическое ранжирование допустимо во время построения единого порядка, но оно не должно зависеть от текущего лимита токенов.

## 6.4. Заполнение свободного бюджета

Реализовать механизм, уменьшающий незаполненный остаток бюджета.

Предпочтительный способ: использовать достаточно мелкие логические чанки и при необходимости дополнять последний фрагмент строками в фиксированном порядке.

Нельзя нарушать вложенность контекста ради заполнения бюджета.

Нельзя добавлять случайный или нерелевантный код только для достижения высокой утилизации.

Ориентировочная исследовательская цель: использование не менее 95% бюджета на большинстве задач, где существует достаточно полезного кода.

Это не обязательный критерий корректности. Качество поиска важнее процента заполнения.

## 6.5. Учёт токенов

Необходимо учитывать:

- содержимое кода;
- имена файлов;
- номера строк;
- заголовки функций;
- служебные разделители;
- дополнительные сигнатуры и метаданные, передаваемые модели.

Для всех сравниваемых алгоритмов использовать одинаковый способ подсчёта токенов.

Если доступен токенизатор целевой модели, использовать его. Иначе применять существующий оценщик и явно указывать, что число токенов приблизительное.

Не выдавать приблизительный подсчёт за точное количество токенов Gemma.

Запрещено превышать указанный бюджет согласно выбранному и документированному счётчику.

## 6.6. Формат контекста

Пример:

`# File: src/auth.py`  
`# Function: AuthService.login`  
`# Lines: 42-58`

Далее идёт исходный код соответствующего фрагмента.

При переходе между файлами добавлять аналогичный заголовок.

Служебные метаданные должны быть минимальными и понятными.

Не добавлять эталонные исправления, целевые функции из разметки SWE-bench или диагностические подсказки, которые раскрывают ответ.

# 7. Retrieval Diagnostics

## 7.1. Цель

Сделать работу алгоритма полностью наблюдаемой для исследователя.

Для каждой задачи сохранять машиночитаемый диагностический отчёт.

## 7.2. Диагностика бюджета

Сохранять:

- идентификатор задачи;
- алгоритм;
- конфигурацию;
- бюджет;
- фактическую или оценочную стоимость контекста;
- количество оставшихся токенов;
- процент использования бюджета;
- число выбранных файлов;
- число выбранных функций;
- число выбранных чанков.

## 7.3. Диагностика кандидатов

Для каждого кандидата:

- идентификатор;
- файл;
- функция;
- диапазон строк;
- оценка релевантности;
- размер;
- выбран или отклонён;
- причина отклонения.

Примеры причин:

`budget_exceeded`  
`duplicate_content`  
`low_relevance`  
`missing_dependency`  
`invalid_chunk`

Фиксировать реальные причины, а не назначать их постфактум.

## 7.4. Диагностика ошибок поиска

На этапе оценки сопоставлять результаты с эталонными патчами SWE-bench.

Выделять случаи:

1. Правильный файл найден, нужная функция пропущена.
2. Файл не найден, хотя соседние функции найдены.
3. Нужный фрагмент имел высокий рейтинг, но не поместился в бюджет.
4. Бюджет заполнен низкорелевантным кодом.
5. Разбиение функции привело к потере нужного участка.

Сформировать отдельный отчёт по задачам, на которых PathPack v0.4 проигрывает BM25 или предыдущему PathPack.

**Строгая изоляция:** разметка правильных функций и эталонные патчи доступны только модулю оценки. Они не должны попадать в retrieval, ranking, chunking или packing.

# 8. Benchmark Framework

## 8.1. Датасет

Использовать SWE-bench Verified.

Текущая экспериментальная выборка:

- 20 dev-задач;
- 60 test-задач.

Сохранить существующее разбиение и идентификаторы задач, не перемешивать их без необходимости.

Поскольку результаты прежнего test уже просматривались, считать этот test исследовательской выборкой, а для окончательного подтверждения подготовить новый независимый holdout.

Не использовать задачи финального holdout для настройки коэффициентов или выбора победившей версии.

## 8.2. Сравниваемые алгоритмы

Обязательные:

- BM25;
- Graph Expansion;
- PathPack v0.2;
- PathPack v0.3;
- PathPack v0.4.

Добавить embedding retrieval как отдельный baseline, если зависимости и веса модели доступны.

Для эмбеддингов использовать фиксированную локально доступную модель, явно документировать её название и версию. Не выполнять скрытые облачные API-вызовы.

Все методы сравнивать на одинаковых задачах и бюджетах с одинаковым учётом токенов.

## 8.3. Основные метрики

**File Recall@Budget**

Доля эталонных файлов, покрытых выбранным контекстом, усреднённая по задачам.

**Function Recall@Budget**

Доля эталонных функций, представленных выбранным контекстом.

Проверить существующую реализацию этой метрики, особенно после внедрения чанкинга.

Нельзя засчитывать функцию как полноценно найденную только потому, что в контексте упомянуто её имя.

Определить и документировать, что считается покрытием функции. Желательно отдельно измерять покрытие изменённых строк кода.

**Latency**

Время формирования контекста, отдельно от построения графа и индексации.

**Token Utilization**

Доля использованного бюджета токенов.

**Useful Functions per 1K Tokens**

Плотность полезных функций в переданном контексте.

Для каждой метрики определить точный знаменатель и способ усреднения.

## 8.4. Разметка эталонных функций

Эталонные функции определять из патчей относительно исходного `base_commit`.

Учитывать:

- методы классов;
- вложенные функции;
- изменённые строки;
- функции, которых ещё не было до патча;
- изменения на уровне модуля;

# 12. Обязательные тесты

Не ограничиваться проверкой того, что программа запускается.

Проверить следующие инварианты.

**Budget Safety**

Выбранный контекст не превышает доступный бюджет по используемому счётчику токенов.

**Budget Monotonicity**

Контекст при 1024 токенах является префиксом контекста при 2048, а контекст при 2048 — префиксом контекста при 4096.

**Determinism**

При одинаковых входных данных и конфигурации алгоритм возвращает одинаковые результаты.

**No Duplicate Content**

Один и тот же фрагмент исходного кода не включается повторно без необходимости.

**Graph Integrity**

Чанки ссылаются на существующие функции и корректные исходные файлы.

**No Gold Leakage**

Эталонные патчи и ответы не используются для поиска и ранжирования.

**Baseline Compatibility**

Существующие алгоритмы BM25, Graph Expansion и PathPack v0.2/v0.3 продолжают работать.

**Metric Correctness**

Проверить метрики на маленьком искусственном датасете, где правильный ответ известен заранее.

**Robustness**

Алгоритм корректно обрабатывает пустые файлы, синтаксические ошибки, отсутствующие связи, слишком длинные функции и очень маленькие бюджеты.

После завершения все старые и новые тесты должны проходить.
